# Замеры производительности и надёжности

Инструменты не меняют код сервиса, поэтому одинаково работают на `main` («до») и на ветке с изменениями («после»).

- `cmd/loadgen` — нагрузка на Kafka, наполнение БД, замер старта, выгрузка order_uid
- `loadtest/k6/get_order.js` — нагрузочный тест HTTP API ([k6](https://k6.io))

## Правила замеров

- Каждый замер повторить **3 раза** и брать медиану.
- Сервис запускать собранным бинарником, а не через `go run` — иначе в замер попадает компиляция:
  ```bash
  go build -o bin/service ./cmd/service      # Windows: -o bin/service.exe
  ```
- Записывать условия: железо (CPU, RAM), ОС, Docker Desktop или Linux, 1 партиция Kafka, число товаров в заказе.
- Во время замера закрыть тяжёлые программы.

## 1. Пропускная способность консьюмера

Сколько заказов в секунду сервис забирает из Kafka и сохраняет в PostgreSQL.

```bash
./bin/service                                  # терминал 1
go run ./cmd/loadgen produce -n 10000          # терминал 2
```

`produce` отправляет 10 000 заказов (по 3 товара) батчами, ждёт, пока каждый заказ окажется в БД или в DLQ (или 30 секунд не будет прогресса), и печатает:

```
orders sent:      10000
orders in DB:     10000
items in DB:      30000 (expected 30000)
sent to DLQ:      0
lost:             0
elapsed:          ...
throughput:       ... orders/s
```

`items in DB` проверяет целостность: меньше ожидаемого — потеря данных, больше — дубли. `lost` — заказы, которых нет ни в БД, ни в DLQ.

## 2. Надёжность: перезапуск сервиса и сбой БД под нагрузкой

```bash
./bin/service                                  # терминал 1
go run ./cmd/loadgen produce -n 10000          # терминал 2
```

Пока идёт `stored X / 10000`:

1. **Перезапуск сервиса:** `Ctrl+C` в терминале 1 и сразу `./bin/service` снова.
2. **Сбой БД:** `docker stop wb-postgres`, подождать 2–3 секунды, `docker start wb-postgres`.

Ожидаемый итог после перезапуска сервиса: `orders in DB = 10000`, `items in DB = 30000`, `sent to DLQ = 0`.

> **Сбой БД и DLQ.** Консьюмер пробует сохранить заказ 5 раз с паузами 0,2 + 0,4 + 0,8 + 1,6 с — около 3 секунд.
> Остановка и запуск контейнера PostgreSQL занимают больше, поэтому текущее сообщение,
> скорее всего, уйдёт в DLQ. Оно не потеряно — лежит в `orders-dlq`, — но в БД его не будет:
> итог будет `orders in DB = 9999`, `sent to DLQ = 1` (или 2). Строка `sent to DLQ` это и показывает.
> Потерянным считается заказ, которого нет ни в БД, ни в DLQ.

## 3. Время ответа API: кэш против БД

```bash
go run ./cmd/loadgen ids -n 1000               # 1000 последних order_uid -> loadtest/k6/ids.txt
```

**С кэшем** (обычный запуск):

```bash
./bin/service
k6 run loadtest/k6/get_order.js
```

**Без кэша** — TTL в 1 мс, запись истекает сразу, каждый запрос идёт в БД:

```bash
CACHE_TTL=1ms ./bin/service                    # PowerShell: $env:CACHE_TTL="1ms"; .\bin\service.exe
k6 run loadtest/k6/get_order.js
```

Сравнивать `http_req_duration` p50 / p95 / p99. Для поиска предела сервиса поднимать частоту: `k6 run -e RATE=2000 loadtest/k6/get_order.js` — пока p99 не начнёт резко расти или не появятся ошибки.

Долю попаданий в кэш показывает Prometheus (http://localhost:9090):

```
rate(cache_hits_total[1m]) / (rate(cache_hits_total[1m]) + rate(cache_misses_total[1m]))
```

## 4. Время старта с прогревом кэша

```bash
go run ./cmd/loadgen seed -n 100000            # один раз: +100 000 заказов в БД
go run ./cmd/loadgen startup -bin ./bin/service
```

`startup` запускает сервис и меряет время до первого успешного `/health`. HTTP-сервер стартует после прогрева кэша, поэтому это время включает прогрев.

> **Ловушка на `main`:** старый прогрев на 100 000 заказов не укладывается в `POSTGRES_TIMEOUT` (5 с),
> падает с Warning, и сервис стартует с пустым кэшем — время выглядит маленьким, но кэш не прогрет.
> Чтобы честно замерить старый прогрев, на `main` увеличить таймаут: `POSTGRES_TIMEOUT=30m`.
> В логе сервиса проверить, что прогрев прошёл без Warning.
